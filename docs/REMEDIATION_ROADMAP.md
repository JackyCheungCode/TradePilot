# TradePilot 系统整改路线图

> 基线分支：`develop`  
> 基线提交：`ac1d21312de3f05ecc0a0b9f583c70286655d459`  
> 文档性质：审计后的整改计划；不是已完成项清单。  
> 原则：先安全与数据正确性，再业务闭环，最后统一体验和性能。每个阶段独立 PR、独立验收，不把多个高风险改动塞进一次部署。

## 1. 目标与范围

将 TradePilot 从多个独立业务页面和渠道工作流，收敛为具有统一身份权限、企业实体、任务状态、来源追踪、客户经营和交易流程的业务平台。

本计划覆盖：
- 全站 Odoo 风格 UI 和响应式交互；
- 全球市场情报与多渠道潜客发现；
- 企业实体、网站、社交账号、商品等对象识别；
- 任务执行中心、采集、Agent 和 API Provider；
- CRM、销售采购、报价与单据；
- Supabase 安全、迁移、可观测性和自动化测试。

不在本计划中默认执行的事项：
- 不删除或重建生产数据；
- 不直接关闭 RLS；
- 不批量删除未使用索引；
- 不自动变更生产密钥或 OAuth 凭据；
- 不将 CI 通过视为第三方 API 的真实端到端验证；
- 不在没有备份、迁移演练和回滚方案时执行破坏性数据库变更。

## 3. 阶段 0：基线与证据固化

### 工作项
1. 固定审计提交 SHA、生产 Worker 版本和部署时间。
2. 导出 Supabase 表、列、主外键、唯一约束、检查约束、RLS、索引和迁移历史。
3. 对比 Git 迁移文件与数据库已应用迁移；逐条确认差异原因，不按文件名猜测。
4. 盘点 Worker 路由的认证方式、Service Role 使用点、所有写操作和外部网络请求。
5. 盘点所有 Provider 的密钥来源、超时、重试、额度和成本记录。
6. 形成数据库备份及恢复演练步骤；先验证恢复可行，再开始高风险变更。

### 验收标准
- 每个 P0 风险有文件/函数/表/策略级定位。
- 数据库迁移差异分为已应用、未应用、名称/版本漂移、数据库手工变更四类。
- 有可执行的备份恢复流程，且恢复演练不覆盖生产库。
- 生产环境配置与代码期望值之间的差异已记录。

## 4. 阶段 1：安全与数据访问（P0）

### 工作项
1. 建立身份与权限矩阵：用户、角色、资源、操作、数据归属。
2. 为用户数据表定义统一归属字段和 RLS 策略；系统级公共表单独定义访问策略。
3. 对 Worker 每个 Service Role 查询逐项审查：身份是否已验证、owner_id 是否来自可信身份、关联记录是否同属该 owner。
4. 对创建、更新、删除和批量操作实施对象级授权检查，不能只验证登录状态。
5. 修复 SSRF：解析 DNS 后检查全部 A/AAAA 地址，拒绝私网、回环、链路本地、保留地址；每次重定向重新验证目标；限制重定向次数、响应体大小、超时和并发。
6. 对 API Key、OAuth Token、Webhook Secret 实施加密存储、脱敏展示和最小权限。
7. 开启并验证 Supabase Auth 泄露密码保护（需确认项目套餐/设置支持情况）。

### 验收标准
- 两个不同 owner 的用户无法读取、更新、删除或通过关联对象间接访问对方数据。
- 未登录请求、伪造 owner_id、越权关联 ID、批量越权操作均有自动化负向测试。
- Service Role 只在 Worker 服务端使用，绝不返回浏览器。
- SSRF 测试覆盖 localhost、IPv4/IPv6 私网、DNS 指向私网、重定向到私网、DNS 重绑定场景。
- 所有拒绝访问行为有明确且不泄露敏感信息的错误码。

## 5. 阶段 2：数据库与迁移治理（P0）

### 工作项
1. 建立数据库 Schema Snapshot 与 migration ledger 对账。
2. 处理迁移版本/命名漂移：保留历史证据，不通过改写生产 migration history 来“让检查通过”。
3. 所有新增变更采用前向兼容迁移：先加字段/表，再部署兼容代码，再回填，最后收紧约束。
4. 关键业务约束放入数据库：外键、唯一键、状态检查、必要的非空约束。
5. 将订单创建、订单明细、事件记录等需要一致成功/失败的操作放入事务或原子 RPC。
6. 为重试型 API 设计 idempotency key，避免重复建单、重复转化、重复采集。
7. 索引仅根据查询计划、表规模和真实负载调整；不因顾问标记“未使用”就直接删除。

### 验收标准
- 空数据库可按迁移顺序构建到当前 Schema。
- 现有数据库升级后 Schema 与预期快照一致。
- 每次迁移都有前置条件、影响评估、回滚/前向修复方案。
- 订单与明细、业务记录与事件日志不会出现半成功状态。
- 迁移在 staging 至少完整演练一次。

## 6. 阶段 3：企业实体与多渠道数据统一（P1）

### 核心对象
- Company：企业主体；
- Website：网站/域名；
- Contact：自然人或业务联系人；
- Social Account：社交账号/主页；
- Product：商品；
- Discovery Observation：某渠道发现的一条原始观察记录；
- Source Attribution：渠道、关键词、任务、URL、时间和原始证据。

### 工作项
1. 每个渠道只负责写入原始观察记录，不自行发明一套企业主档。
2. 统一 Entity Resolution 服务，按外部 ID、域名、电话、邮箱域名、名称、地址和地理距离进行分层匹配。
3. 匹配输出为 exact / high / possible / no-match，并保存匹配证据和分值。
4. 对 possible 匹配进入人工审核，不自动合并。
5. 企业合并采用可审计操作，保留被合并 ID 的 redirect/alias 和全部来源。
6. 商品、社交账号、网站、个人不能默认创建为 Company。
7. 统一来源归因：同一企业可有多个发现渠道、多个任务和多条原始结果。

### 验收标准
- 同一企业从 Google、Facebook、Instagram、地图等渠道发现后可归并并保留所有来源。
- 同名不同城市/分店不会仅凭名称被合并。
- 每次自动匹配均可解释依据；人工合并可撤销或通过审计记录恢复。
- 商品搜索结果不会错误进入企业客户池。

## 7. 阶段 4：任务与联系方式采集可靠性（P1）

### 统一任务状态
`queued → running → completed | partial | failed | cancelled`

任务本身、渠道子任务、采集步骤、Agent 执行分别拥有状态，禁止用父任务状态覆盖子步骤真实结果。

### 工作项
1. 统一任务状态转换规则及合法迁移表。
2. 任务记录保存 progress、processed_count、success_count、failure_count、retry_count、started_at、finished_at、last_error、provider usage。
3. 支持渠道级失败和部分成功，并能从失败步骤恢复。
4. 任务取消要能传播到下游任务和外部请求；无法取消的请求标记为 cancel_requested。
5. 每个渠道写入使用幂等键，重试不重复生成企业或观察记录。
6. 联系方式按单项保存 evidence URL、原始值、规范化值、采集时间、验证状态和置信度。
7. 对官网重定向实行同源/允许域规则，跳转目标每次重新执行 SSRF 校验。
8. 静态 HTML、JSON-LD、联系页面、社交链接分层采集；浏览器渲染只作为可配置的后备步骤。

### 验收标准
- 任意一个渠道失败但其他渠道成功时，任务状态准确显示 partial。
- 重试同一个任务不会重复写入同一来源观察。
- 联系方式每个字段都能追溯来源页面。
- 采集结果不会把图片文件名、静态资源路径误识别成邮箱或联系方式。
- 任务在页面刷新后状态、日志、结果和计数保持一致。

## 8. 阶段 5：CRM 经营闭环（P1）

### 工作项
1. 明确 Lead、Company、Contact、Opportunity 的生命周期和转换规则。
2. 线索转客户时使用事务，保证企业、联系人、商机和来源关联一致。
3. 统一电话、邮箱、域名规范化，提供重复提示和合并流程。
4. 关联字段使用可搜索记录选择器，不要求用户输入 UUID。
5. 增加客户活动时间线：邮件、电话、WhatsApp、会议、备注、任务和系统事件。
6. 商机阶段定义进入条件、退出条件、概率、预计金额、赢单/输单原因。
7. 跟进任务具有负责人、截止时间、提醒、完成结果和关联客户。
8. 修复姓名解析等字段映射问题，并增加中英文、多空格、单名、复合姓氏测试。

### 验收标准
- 从发现结果转为 CRM 客户只产生一个目标企业，不丢失原始来源。
- 客户、联系人、商机之间关联完整。
- 重复转化请求幂等。
- 客户详情可以看到完整活动和来源历史。
- 关键阶段变更记录操作者、时间和原因。

## 9. 阶段 6：销售采购与单据（P1）

### 工作项
1. 定义报价、销售订单、采购订单、商业单据的状态机。
2. 报价确认后生成关联销售订单，保留报价版本快照。
3. 销售订单与采购订单通过明确的履约/采购关联，不以名称或文本字段松散关联。
4. 统一币种、税额、折扣、单位、汇率和舍入规则。
5. 订单、明细、库存/交付状态、事件日志等关键写操作事务化。
6. 单据模板版本、生成快照、PDF 和源业务记录建立可追溯关系。
7. 对撤销、作废、重新生成和版本升级制定明确规则。

### 验收标准
- 报价转订单不会丢失客户、产品、变体、价格、币种和条款。
- 同一个报价不能被重复生成多笔订单，除非业务规则明确允许部分转单。
- 历史 PDF 可按生成时模板快照复现。
- 订单状态变更和事件日志原子成功或原子失败。

## 10. 阶段 7：AI / Agent / Provider 治理（P1）

### 工作项
1. 定义 Agent 输入输出 JSON Schema、版本和错误协议。
2. 区分事实、推断、建议；每条事实有来源证据。
3. 对模型输出做 Schema 校验和失败重试，禁止未经校验的自由文本直接驱动业务写操作。
4. 完成 OAuth2 授权、Token 加密存储、刷新、过期和撤销；未完成前隐藏或禁用 OAuth2 选项。
5. 统一 Provider Adapter：超时、重试、限流、错误映射、用量、成本和请求追踪。
6. 建立每任务、每日、每 Provider 的预算和硬限制。
7. Agent 对外写入、发送消息、创建订单等动作必须走权限检查和审批策略。

### 验收标准
- Agent 输出符合版本化 Schema，非法结果不会进入业务表。
- 每条 AI 事实和建议可追溯到模型调用和证据。
- OAuth Token 不出现在日志和前端响应。
- 预算超限后按策略阻止或要求审批。
- Agent 成功、部分成功和失败状态准确映射到父任务。

## 11. 阶段 8：Odoo 风格全站 UI（P2）

### 统一设计原则
- 背景层级组织信息，极少量边框辅助结构。
- 主导航清楚、面包屑稳定、页面标题和主操作一致。
- 桌面端优先使用高信息密度列表；支持 List、Kanban、Form 的场景化切换。
- 搜索、筛选、分组、排序、收藏搜索形成统一控制系统。
- 业务记录使用统一状态、动作菜单、关联记录和活动时间线。
- 移动端统计/选择卡片两列；业务列表转换为移动卡片；复杂表单分区；宽表格提供适配方案。
- 不用浏览器原生下拉菜单替代项目自定义选择器。
- 保留用户已确认的侧边栏层级、黑色品牌主色与白色侧栏方向。

### 执行顺序
1. Design Tokens、字体、间距、颜色、圆角、阴影。
2. AppShell、Sidebar、Topbar、Breadcrumb、PageControlPanel。
3. SearchControl、FilterBuilder、GroupBy、Sort、Saved Search。
4. DataTable、Kanban、MobileRecordCard。
5. FormSection、RelationPicker、StatusBadge、ActionMenu。
6. ActivityTimeline、Chatter、Empty/Error/Loading State。
7. 按模块迁移页面：市场情报 → CRM → 主数据 → 订单 → 单据 → Agent → 设置。

### 验收标准
- 每个核心页面通过桌面宽屏、平板、手机三种视口检查。
- 交互控件键盘可用、焦点可见、标签和错误信息可访问。
- 搜索/筛选/分组/排序在刷新和返回页面后行为一致。
- 移动端无意外横向溢出；列表、表单和统计卡片采用各自合理布局。
- 同一类操作在不同模块的行为与反馈一致。

## 12. 阶段 9：质量门禁与可观测性（贯穿全程）

### CI 必须包含
- TypeScript typecheck；
- lint；
- 单元测试；
- Worker 构建；
- 前端构建；
- 迁移静态检查；
- 关键权限与状态机集成测试；
- 核心业务 E2E（至少覆盖发现→结果→CRM→报价/订单）。

### 运行时观测
- request_id / trace_id；
- task_id / provider_call_id；
- owner_id 使用不可逆或受控关联标识，日志不暴露个人数据；
- API 错误分类、重试、耗时；
- Provider 用量与成本；
- 任务成功率、部分成功率、失败率和排队时长；
- CRM 转化率和重复合并率。

### 验收标准
- 生产错误可以从 request_id 定位到 Worker 路由、数据库操作和 Provider 调用。
- 核心业务流程有自动化测试。
- CI 失败禁止合并；部署后执行健康检查和版本确认。
- 架构文档与真实实现同步更新。

## 13. PR 与发布纪律

1. 每个阶段拆成可审查的小 PR，建议一个 PR 只解决一个风险主题。
2. 数据库变更与应用代码变更明确依赖顺序。
3. 每个 PR 说明风险、数据影响、回滚方案、测试范围和未覆盖范围。
4. 高风险权限变更先在 staging 验证两个不同 owner 的正反向访问。
5. 生产部署后核对 Worker 版本、100% 流量、健康检查和错误率。
6. 不把“构建成功”写成“真实 API 流程已验证”。
7. 每次发布保留前一生产版本和可执行回滚步骤。

| 2 | 审查全部 Worker 路由 | 输出身份校验、对象归属和写操作检查清单 |
| 3 | 修复 P0 越权风险 | 两用户隔离测试全部通过 |
| 4 | 迁移历史与 Schema 对账 | 无未解释差异，形成迁移基线 |
| 5 | SSRF 与外部请求安全修复 | DNS/重定向/私网测试通过 |
| 6 | 任务状态机统一 | partial 不再被映射为 succeeded/completed |
| 7 | 修复 UI 选择器命名不一致 | 手机端目标页面实测两列 |
| 8 | 建立跨渠道实体统一设计与迁移方案 | 不直接合并生产数据，先完成匹配评估 |

## 15. 风险登记与决策边界

- RLS 策略必须按真实数据模型制定，不能简单给 33 张表统一添加 `auth.uid() = owner_id`；部分表可能通过父记录归属，部分表可能是共享字典或系统配置。
- 数据迁移必须先做只读盘点和备份验证，不能为消除版本差异而直接修改 `schema_migrations`。
- 企业去重不能仅按名称自动合并；必须保存匹配证据并支持人工审核。
- 任务状态迁移需要兼容旧记录，旧状态回填应单独脚本化并可重复执行。
- 订单事务化需确认现有调用方和外部副作用，避免把邮件、PDF、第三方 API 调用放入长事务。
- Odoo UI 改造不应改变已确认的业务规则和数据结构，视觉重构与业务重构分开提交。

## 16. 完成定义（Definition of Done）

只有同时满足以下条件，才能认为本轮整改完成：
1. P0 安全与迁移风险已关闭并有自动化回归测试。
2. 跨渠道企业识别、来源追踪和任务状态在所有渠道统一。
3. 联系方式、CRM、订单和单据的关键业务操作可追溯、幂等且数据一致。
4. Agent 输出可验证、可追溯，外部动作有权限控制。
5. 全站核心页面符合统一 Odoo 风格设计系统和移动端验收标准。
6. CI、部署后检查、日志和业务指标能持续发现回归。
7. 产品文档、数据字典、API 契约和迁移历史与当前代码一致。
